# IGNでPressure受信を使って制御する設計ガイド

このドキュメントは、実装方法そのものより先に、設計の意味を理解するためのガイドです。
目的は次の2つです。

- Pressureのパケットを受信して、条件成立時に50Hz制御を回す
- 条件が未成立の間は、状態パケットを約1Hzで送る

## 1. まず全体像を理解する

IGNの処理は、役割の違う3つの場所に分けます。

1. setup
- 起動時に1回だけ実行
- 通信の受信設定やタイマ開始など、初期化だけを行う

2. loop
- 常時繰り返し実行
- 受信キューからパケットを取り出し、最新状態に反映する

3. callback
- タイマ周期で呼ばれる
- 周期性が必要な処理だけを実行する
- ここでは50Hz制御の実行タイミングを保証する

この分離をすると、受信待ちや通信遅延で制御周期が崩れにくくなります。

## 2. なぜPressure受信はloop側で扱うのか

理由は、受信処理の実行時間が読みにくいからです。

- 受信キューに何件溜まるかは時々刻々で変わる
- パケットの欠損や再送などで処理時間がぶれる
- callback内で重い処理をすると、50Hzの周期が崩れる

そのため、次の責務分割が安全です。

- loop: 受信、パース、最新値の保持
- callback: 保持済みの最新値を使って制御実行

言い換えると、loopは情報更新、callbackは時間管理です。

## 3. データの流れを言語化する

IGN内部では、Pressureパケットをそのまま制御に渡すのではなく、最新値として保持します。

1. loopでPressureパケット受信
2. 必要なフィールドを抽出
- PA: 圧力高度
- PR: 圧力
- Ts: 必要ならデータ鮮度判定
3. メンバ変数を更新
- latest_altitude_m
- latest_pressure_pa
- last_pressure_ms
4. フラグ判定に使う内部状態を更新
- control_active

callbackはこの最新値を読むだけにします。

## 4. フラグ設計の考え方

フラグは、制御開始のトリガです。単純なしきい値だけでなく、誤作動を防ぐ条件を組み合わせるのが実運用向きです。

設計要素は次の通りです。

1. しきい値条件
- 例: PAが30m以上

2. 連続成立回数
- 例: 3サンプル連続で成立したら有効
- ノイズで1回だけ超えたケースを除外できる

3. データ鮮度チェック
- 例: 現在時刻 - last_pressure_ms が200ms以内
- 古いデータを使って制御しない

4. ラッチの有無
- 一度有効になったら戻さないか
- 条件を外れたら無効へ戻すか
- 点火系では安全側設計が必要

## 5. 50Hz制御の意味

50Hzは、20msごとに制御計算を行うという意味です。

- 周期が一定に近いほど制御しやすい
- callbackを20ms周期にすると、制御タイミングの基準が明確になる
- callback内は短時間で終わる処理に限定する

callback内でやることは最小限にします。

- control_activeがtrueなら制御関数を1回呼ぶ
- falseなら重い処理は行わない

## 6. 1Hz送信を同居させる意味

フラグ未成立時は、機体状態を地上に見せるために低頻度送信が必要です。
ただし50Hzで毎回送ると帯域とCPUを無駄に使います。

そのため、50Hzタイマをそのまま使って分周します。

- 50Hzタイマのティックをカウント
- 50ティックごとに1回送信
- 結果として約1Hz送信

この方法の利点

- タイマを増やさずに済む
- 周期基準が1つなので設計が単純
- デバッグ時に時間軸を追いやすい

## 7. 推奨する内部状態

IGNで持つと設計しやすい状態の例です。

- latest_altitude_m: 最新高度
- latest_pressure_pa: 最新圧力
- last_pressure_ms: 最終受信時刻
- control_active: 制御有効フラグ
- activate_threshold_m: 有効化高度しきい値
- consecutive_count: 条件連続成立回数
- tick_count: 50Hzティック数
- inactive_telemetry_divider: 非アクティブ時の送信分周値

## 8. 異常時の考え方

実機では正常系より異常系の定義が重要です。

1. Pressureが来ない
- 一定時間更新なしならデータ無効
- control_activeを安全側へ遷移
- 異常コードをテレメトリ送信

2. 値が不自然
- PAやPRがレンジ外なら破棄
- 連続異常回数で故障判定

3. キューがあふれる
- 受信キューサイズを見直す
- loop側で毎回処理上限を設ける

## 9. テレメトリ設計の意味

1Hzで送る内容は、地上局が状態推定しやすい項目を優先します。

最低限推奨

- Ac: 制御有効フラグ
- PA: 最新高度
- PR: 最新圧力
- Ts: 送信時刻
- Er: 可能ならエラー状態

この構成にすると、なぜ制御に入らないかを地上で説明しやすくなります。

## 10. 実装前チェックリスト

- setupでPressure用Listenerを初期化する設計になっている
- loopで受信して最新値へ反映する責務分離ができている
- callbackは20ms周期で短い処理に限定されている
- 50Hz制御と1Hz送信の条件分岐が明確
- データ鮮度チェックがある
- フラグの有効化条件と解除条件が文章化されている
- 異常時の安全側動作が定義されている

## 11. 典型的な状態遷移

1. 起動直後
- control_active=false
- 1Hzで状態送信

2. Pressure受信開始
- latest値更新
- しきい値判定を評価

3. 条件成立
- control_active=trueへ遷移
- callbackごとに50Hz制御

4. 条件不成立または異常
- 方針に応じてfalseへ戻す、またはラッチ保持
- 必要なら1Hz状態送信に戻る

## 12. まとめ

設計のコアは次の一文です。

- 受信の不確実性はloopで吸収し、制御の時間確実性はcallbackで担保する

この考え方で組むと、Pressure入力に基づくフラグ駆動制御と、待機時1Hz送信を同時に安定運用しやすくなります。
