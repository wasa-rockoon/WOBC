# テレメトリは届くがアップリンク・ACKを確認できない原因

> 2026-09-05解消確認: ユーザーがCOM21モニタの起動ディレクトリを`C:\WOBC`へ変更し、定期テレメトリとACKの受信を実機確認した。確認値と全体の変更履歴は[統合作業ログ](20260905_telemetry_uplink_ack_worklog.md)を参照。以下の調査データは解消前の記録。

調査日: 2026年9月5日  
実機の接続: Tracker = COM19、GOLIDEN = COM21

## 結論

今回確認したPC側の不通原因は、**コマンド作成側とモニタ側が別の`.command`ファイルを使っていたこと**。
作成したコマンドはモニタに読み込まれておらず、COM21へのシリアル送信に進んでいなかった。

加えて、作成済みコマンドの最終更新は現在のモニタ起動より前だった。
`wcpp-util`は起動時にファイル末尾へ移動するため、監視先を直した後も、新しくコマンドを追記する必要がある。

今回の現象だけを根拠に、LoRaの衝突やTrackerのACK生成処理が原因だと判断することはできない。
原因調査時点では修正手順での実機成功は未確認だったが、その後、ユーザーによって起動ディレクトリ修正後のアップリンク／ACK成功と定期テレメトリの併用が確認された。

## 確認できた証拠

### 1. コマンド作成先には正常なパケットがある

| ファイル | サイズ | 最終更新 | 内容 |
| --- | --- | --- | --- |
| `C:\WOBC\.command` | 278 byte | 2026-09-05 20:26:57 | 正常な`'t'` commandが17件 |
| `C:\Users\numat\.command` | 0 byte | 2025-09-11 14:57:27 | 空。現在の2つのモニタの監視先 |
| `C:\WOBC\src\library\wcpp\.command` | 0 byte | 2026-04-06 22:40:23 | 別の空ファイル |

`C:\WOBC\.command`を、稼働中モニタと同じインストール済み`wcpp.util.parse_packet()`で読み込んだところ、
17件すべてが`'t'` commandとして正常に復号できた。Component IDはいずれも`0x10`。
フレームの長さ・チェックサム・終端も確認しており、パケット作成自体の失敗ではない。

### 2. 稼働中モニタの起動フォルダが異なる

| PID（調査時点） | 起動コマンド | 起動フォルダ | 起動時刻 |
| --- | --- | --- | --- |
| 63632 | `wcpp-util`（ポート自動選択） | `C:\Users\numat` | 20:31:49 |
| 52852 | `wcpp-util -p COM19` | `C:\Users\numat` | 20:33:08 |

実行されていたのはAnaconda環境の`wcpp-util.exe`で、読み込まれていた実装は次のファイルだった。

```text
C:\Users\numat\anaconda3\Lib\site-packages\wcpp\util.py
```

その実装は次のように相対パスでファイルを開く。

```python
command_file = open('.command', mode='rb')
command_file.seek(0, 2)
```

したがって、両モニタは`C:\Users\numat\.command`を監視する。
`send_command.py`が別フォルダのファイルへ正常に追記しても、そこへ自動的に追従する仕組みはない。

### 3. 画像とも整合する

- COM21にはTracker由来の`'M'`と`Ss`があり、無線ダウンリンクは確認できる。
- 提示されたCOM21のツリーには、PCが送信した`'t'`の項目が見えない。
- `util.py`はファイルからコマンドを読み込むと、シリアル送信前にそのコマンドをツリーへ登録する。
- COM19にも`'t'`のLoRa受信やACK関連の表示が見えない。

画像だけで断定したのではなく、プロセスの起動フォルダ、監視実装、ファイル内容を照合して原因を確認した。

### 4. ユーザー確認との照合

ユーザーから、生成コマンドは以下で、モニタ起動にはAnaconda Promptから
`wcpp-util -p COM21`／`wcpp-util -p COM19`を使用し、COM21に`sent packet`は表示されなかったとの回答を得た。

```powershell
python src/library/wcpp/python/send_command.py --packet-id t --component-id 0x10 --data "uplink"
```

生成コマンドに`--command-path`はなく、起動フォルダの`.command`へ出力される。
この回答も、作成先と監視先が異なるためモニタの送信処理に進んでいないという調査結果と整合する。
上のプロセス表は調査時にOSから取得した値であり、ユーザー申告の起動コマンドとは分けて記録した。

## 再確認の手順

### 1. COM21モニタを終了し、正しいフォルダから起動する

COM21側のモニタを`q`で終了してから、PowerShellで次を実行する。

```powershell
Set-Location C:\WOBC
& C:\Users\numat\anaconda3\Scripts\wcpp-util.exe -p COM21
```

COM21への接続が表示されてから、次のコマンド作成に進む。

### 2. 別のPowerShellから、新しいコマンドを作成する

```powershell
& C:\Users\numat\anaconda3\python.exe C:\WOBC\src\library\wcpp\python\send_command.py --packet-id t --component-id 0x10 --data hello --command-path C:\WOBC\.command
```

`--command-path`を絶対パスで指定することで、作成側の起動フォルダへの依存をなくす。
既存17件を再送するのではなく、モニタ起動後に1件だけ新規作成して確認する。

### 3. Trackerモニタは同じキューファイルを監視させない

現在のCOM19モニタは`C:\Users\numat`で起動しているため、そのまま使用できる。
COM19とCOM21を両方とも`C:\WOBC`から起動すると、両方が同じコマンドを読み取り、それぞれのUSBへ送ってしまう。
TrackerへUSBで直接入ったコマンドには`Ss`がなく、LoRaアップリンクの成功確認にはならない。

この再確認では、COM21だけが`C:\WOBC\.command`を監視する構成にする。

### 4. 成功判定を段階ごとに行う

| 段階 | 確認する表示 | 証明できる範囲 |
| --- | --- | --- |
| ファイル作成 | 作成ツールの`[SUCCESS]` | `.command`への追記成功のみ |
| PC→COM21 | COM21の`'t'`項目と`sent packet` | モニタによる読み込み・シリアル書き込み |
| GOLIDEN→Tracker | COM19で`Ss`付き`'t'`、ACK投入ログ | TrackerがLoRaアップリンクを受信したこと |
| Tracker→GOLIDEN→PC | COM21に`'a'`、`St=0`、`Ri=116`（`'t'`） | ACKが無線で戻りPCへ届いたこと |

`sent packet`まで出るのにTrackerのLoRa受信がない場合は、そこで初めてGOLIDENの無線送信から先を追加調査する。
テレメトリ送信との衝突や送信ガードの影響は、この段階で切り分ける。

## 調査時に行ったこと・行っていないこと

- 稼働中プロセスの起動コマンド・起動フォルダを読み取った。
- 作成済みコマンドを実際のインストール済みパーサで検証した。
- 一時ファイルで「起動前のデータはスキップされ、起動後の追記だけ読み込まれる」動作を再現した。
- シリアルポートのオープン、実機へのコマンド送信、モニタの終了、ファームウェア書き込みは行っていない。
- 今回の調査ではソースコードを変更していない。
