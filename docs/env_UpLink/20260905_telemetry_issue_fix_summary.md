# 常時テレメトリ追加に伴う問題点と修正内容

> 2026-09-05追記: ユーザーが定期テレメトリとアップリンク／ACKの併用を実機確認した。PC側の不通原因の解消も含む最終結果は[統合作業ログ](20260905_telemetry_uplink_ack_worklog.md)を参照。

作成日: 2026年9月5日  
対象: PC ↔ GOLIDEN ↔ Tracker

## 1. 作業の前提

変更前は、PCからのアップリンクをTrackerが受信し、ACKをGOLIDEN経由でPCへ返す通信が実機で動作していた。
今回の目的は、この通信形式を維持しながらTrackerの常時テレメトリ送信を追加すること。

以下の問題点はコード調査で確認したものであり、実機で観測したパケット欠落の原因をすべて特定したという意味ではない。
本資料の初版作成時点ではビルドと模擬通信テストまで確認していた。その後の実機併用確認は上記の統合作業ログに記録した。

## 2. 何が問題で、何を修正したか

| 問題点・追加時の懸念 | 修正内容 | ねらい |
| --- | --- | --- |
| Trackerに、無線の空き時間を考慮した定期テレメトリ送信処理がなかった | 2秒周期で`'M'`パケットを生成。稼働時間と最新GPS・気圧データを格納し、送信可能な場合だけキューへ投入する | アップリンクの受信時間を確保しながら定期送信する |
| ACKとテレメトリの送信優先度を管理する仕組みがなかった | ACK、通常送信、テレメトリの順に送信するキューを追加。キュー操作と送信開始をmutexで排他制御する | テレメトリによってACKを後回しにしない |
| アップリンク受信からMainがACKを生成するまで、別タスクでテレメトリを開始する隙間があった | 対象アップリンクを受信した時点で`awaiting_ack_`を増やす。ACKがキューへ入るまで通常送信・テレメトリを停止する | ACK生成待ちの間にも優先度を維持する |
| 従来の送信処理は、LoRaが約2秒間ビジーだと要求を破棄していた | ビジー時はキュー内に保持し、次の処理周期で再試行する | ローカルのビジーを理由に受理済みACKを捨てない |
| 従来の受信ループには`while (e220_.isBusy()) {}`という無期限待ちがあった | 無期限待ちを撤去し、受信処理を進めてから送信可否を判定する | AUXがLowのままでもLoRaタスクを待ちループに閉じ込めない |
| AUXだけの判定では、UART受信途中や送信後の待機を十分に管理できなかった | AUX、UART未読データ、送信後ガード時間、100 msのアイドル時間を確認。書き込み直前にも再確認する | 受信途中への送信割り込みや送信の重なりを抑える |
| `sendPacket()`による送信要求は、呼び出し側でキュー受理成否を確認できなかった | 両Mainから`queuePacket()`を呼ぶ方式へ変更。投入できないACK・PCコマンドはMainでも保持して再試行する | キュー満杯や一時的な競合に対応する |
| GOLIDENはローカルのGPS等も無線転送対象にしており、追加ログも無線へ流れる可能性があった | Mainの無線送信対象をcommandに限定する | 地上局自身のセンサーデータ・ログによる無線帯域の消費を防ぐ |
| GOLIDENの`Ss`判定をPC転送の拒否と誤解し、受信パケットを再配信すると二重転送になる | 既存のLoRa→kernel→SerialBus経路を維持し、Mainから受信パケットを再配信しない | ACKとテレメトリを同じ経路でPCへ渡し、重複を防ぐ |
| E220受信処理で、同じ長さのパケットが続くと古いタイムアウト起点を使い続けていた。追跡変数も未初期化だった | 追跡変数を初期化し、受信完了ごとに長さ追跡をリセットする | 同一長のテレメトリを長時間受信した際の誤タイムアウトを防ぐ |

## 3. ループ防止と補助的な修正

- Trackerのアップリンクlistenerをcommand限定にし、自分のテレメトリやログをACK対象にしない。
- ACK対象を、LoRa受信マーカー`Ss`を持つ`'t'`／`'c'` commandに限定する。
- Mainからの直接キュー投入はカーネルへ再配信しないため、自分の送信要求を再度拾わない。
- GOLIDENの転送ログは`sendPacket(trace, tx_listener_)`で自listenerを除外する。
- LoRaの従来型送信コマンド処理でも、RF受信由来の`Ss`付きパケットを再送させない。
- 受信パケットの長さ・ヘッダ長・チェックサムを、パケットとして扱う前に検証する。
- GOLIDENでは245 byteを超える送信対象コマンドをログ付きで拒否し、後続の正常な要求を止めない。
- センサー値は最新1件だけをキャッシュし、キャッシュ更新から5秒以上経過した項目は省略する。

## 5. 維持した仕様と、変えた内部処理

維持した仕様:

- 無線のパケット形式: E220長さバイト＋WCPP＋チェックサム。
- チャンネル3、SF9／BW125、透過送信モード。
- ACKのPacket ID `'a'`、`St=0`、`Ri=受信Packet ID`。
- LoRa受信パケットへの`Ss`付与と、SerialBusによるPCへの配信。

変えた内部処理:

- 両Mainでは、従来の`'s'`コマンドの`Pa`にpayloadを包んでカーネルへ投入する方式から、受理成否が分かる`queuePacket(payload, priority)`へ変更した。
- 他の呼び出し元向けの`'s' + Pa`インターフェースは残した。ただし、この旧経路ではキュー受理失敗時にログを出すのみで、Mainの直接投入経路と同じ再試行保証はない。
- GOLIDENのローカルセンサーデータ・ログはPCへ配信するが、無線へは自動転送しない。

## 6. 追加したログ

| ログの先頭 | 何を確認できるか |
| --- | --- |
| `[Tracker] Telemetry sent` | テレメトリをE220へUART送信したこと。無線でPCまで到達したことの証明ではない |
| `[Tracker] Uplink received & ACK sending...` | アップリンクに対するACKが優先キューへ入ったこと |
| `[GOLIDEN] LoRa Rx -> SerialBus Tx (Packet ID: ...)` | GOLIDEN MainもLoRa受信パケットを観測したこと。実際のPC転送は独立したSerialBusが行う |
| `LoRa busy: TX retained for retry` | 送信要求を破棄せず、ビジー解除を待っていること |

ログは既存のWCPP `'#'`パケットとして出力する。USB Serialへ平文は混在させず、`util.py`等のWCPP対応モニタで確認する。

## 7. 検証結果

- `pio run -e Tracker -e GOLIDEN`: 両環境のコンパイル・リンクに成功。
- 実際のLoRa／E220／WCPPソースを模擬UART・AUXで動かす11シナリオに成功。
- 主な確認内容: ACK優先、長時間ビジー後の復帰、ACK生成待ち、UART部分受信、キュー満杯時の再試行、送信直前のビジー変化、送信間隔、`millis()`の桁あふれ、旧`Pa`形式の互換性、同一長RSSIパケットの30秒連続受信。
- テスト終了時に、テスト用パケット領域の未解放がないことを確認。

## 8. 残っている実機確認

今回修正したのは、主にソフトウェア内での送信競合とビジー時の要求破棄である。
送信済みのテレメトリ電波を中断してACKへ切り替えることはできず、無線上の同時送信を完全には防げない。
送信後ガード時間も実測値ではなく、現在の無線設定向けの保守的な初期値である。

実機では次を確認する必要がある。

1. 定期テレメトリを60秒以上受信し、途中停止や二重表示がないこと。
2. 定期送信中に`'t'`／`'c'`を1件ずつ送り、ACKの`St`／`Ri`が正しいこと。
3. テレメトリ送信の前後にコマンドを送り、ACK遅延・欠落率を測定すること。
4. AUXとUART、実際の空中占有時間を観測してガード時間を調整すること。

キューは有限であり、無制限の連続投入やPC側の受信停止まで含む無損失は保証していない。
その後、変更後の実機でテレメトリとアップリンク／ACKの併用を確認した。並行動作の網羅的検証や長時間・高負荷条件での定量評価は引き続き確認対象とする。

詳しい送信条件・テスト実行方法は[実装説明](20260905_continuous_telemetry.md)を参照。
