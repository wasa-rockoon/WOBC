# 常時テレメトリ・アップリンク・ACK通信の統合作業ログ

作業日: 2026年9月5日  
対象: PC ↔ GOLIDEN ↔ Tracker  
実機確認: ユーザーによる動作報告およびCOM21モニタの添付画像

## 1. 最終結果

**Trackerからの定期テレメトリ受信と、PCからのアップリンクに対するACK受信を、同じ運用中に実機で確認できた。**

テレメトリ追加後にアップリンクを確認できなかった直接の原因は、PC側のコマンド作成先とモニタの監視先が異なっていたことだった。
COM21モニタの起動ディレクトリを`C:\WOBC`へ変更したところ、ユーザーからテレメトリのダウンリンクとACKを併せて確認できたとの報告があった。
この不通の解消に際して、ファームウェアの追加変更は行っていない。

本書の「同時確認」は、定期テレメトリを動かした状態でアップリンク／ACKが成立したという意味であり、半二重のLoRaが同時に送受信したという意味ではない。

## 2. 開始時点の状態と目標

開始時点では、次の経路が実機で動作するコードベースへ戻されていた。

```text
PC → GOLIDEN → Tracker：アップリンクコマンド
Tracker → GOLIDEN → PC：アップリンクに対するACK
```

この既存通信に対して、Trackerの常時テレメトリ送信を追加することが今回の目標だった。
特に、ACKとテレメトリの送信競合、ビジー中の送信要求破棄、受信パケットの再送ループを避ける必要があった。

## 4. ファームウェアの実装・変更内容

### 4.1 Trackerの定期テレメトリ

対象: [src/modules/Tracker/main.cpp](../../src/modules/Tracker/main.cpp)

- Mainの処理で2秒周期のテレメトリを生成する。
- Packet IDは`'M'`（`0x4D`）、component IDは`0x00`、origin unitは`0x61`、宛先は`0xFF`。
- 16 bitのsequenceをキュー受理ごとに加算する。
- GPSとPressureのパケットを各1件キャッシュし、Mainからセンサードライバを直接操作しない。
- キャッシュ更新から5秒以上経過したセンサー項目は省略する。GPSの測位有効性は既存コンポーネントの出力仕様に従う。
- ビジー中は延期し、遅れた周期分をまとめて送る動作はしない。
- ACK投入後はMain側のテレメトリ周期をリセットし、アップリンク受信の空き時間を確保する。

| エントリ | 内容 |
| --- | --- |
| `Ts` | 稼働時間、ms |
| `LA`, `LO`, `AL` | GPSの緯度、経度、高度 |
| `PR`, `PA` | 気圧、気圧高度 |

既存GPSコンポーネントの`'M'`はcomponent IDが`0x15`であり、今回のMainの`'M'`とは区別できる。
画面上ではエントリ名が`La`、`Lo`、`Al`等の表記になる場合がある。

### 4.2 ACK優先と送信要求の保持

対象: [lora.h](../../src/components/LoRa/lora.h)、[lora.cpp](../../src/components/LoRa/lora.cpp)、両Main

従来は`'s'`コマンドの`Pa`に送信payloadを入れ、`sendPacket()`で内部配信していた。
この経路ではMainからキュー受理成否を確認できなかったため、両Mainは`queuePacket(payload, priority)`で直接投入する方式へ変更した。
投入失敗時にはMainも対象のACK／PCコマンドを保持し、次回loopで再試行する。
無線に載せるpayloadの形式は維持した。

| 項目 | 実装 |
| --- | --- |
| 優先度 | ACK → 通常送信 → テレメトリ |
| ACKキュー | 8件 |
| 通常送信キュー | 8件 |
| テレメトリ待機 | 1件 |
| Mainの受信listener | 各32件 |
| 排他制御 | FreeRTOS mutexによるキュー操作・送信開始の直列化 |
| 無線ドライバへのアクセス | LoRaタスクに集約 |
| 対象アップリンク受信直後 | `awaiting_ack_`を増やし、ACKキュー投入まで通常送信・テレメトリを止める |

ACK対象は`Ss`付きの`'t'`または`'c'` command。
返信形式は従来どおり`'a'`、`St=0`、`Ri=受信Packet ID`とした。

他の呼び出し元向けに旧`'s' + Pa`インターフェースも残している。
旧経路のキュー受理失敗はログ出力であり、Mainの直接投入経路と同じ再試行動作ではない。

### 4.3 ビジー判定と送信ガード

従来の無期限`while (e220_.isBusy()) {}`と、約2秒ビジーで送信要求を破棄する処理を撤去した。
受信を先に処理し、次の条件を満たす場合に送信する。

- AUXがビジーを示していない。
- UARTに未読データがない。
- 直前の送信後ガード時間を経過している。
- アイドル状態が100 ms続いている。

UART書き込み直前にも状態を確認し、ビジーでE220に受理されなければ要求をキューに残す。
送信後ガードは`200 + (WCPPサイズ + 16) * 10` msを初期値とし、ドライバでもテレメトリのUART送信間隔を最低2秒に制限した。
ガード値は現在のSF9／BW125設定向けの保守的な値であり、実測AirTimeではない。

### 4.4 GOLIDENのルーティングとループ防止

対象: [src/modules/GOLIDEN/main.cpp](../../src/modules/GOLIDEN/main.cpp)

LoRa受信からPCへの配信は、既存の次の経路を使用する。

```text
LoRa受信 → チェックサム検証・Ss付与 → kernel → SerialBus → USB → PC
```

Mainの`Ss`判定は、PC転送を拒否する処理ではなく、無線への再送を防ぐ処理だった。
この経路を維持し、ACKもテレメトリもMainから二重に再配信しない。

- Mainの無線送信対象をcommandに限定し、GOLIDEN自身のGPS・電源・ログの自動無線転送を止めた。これらはPCには引き続き配信される。
- 追加した転送ログは`sendPacket(trace, tx_listener_)`で自listenerを除外した。
- Trackerのlistenerをcommand限定にし、自分のテレメトリ・ログをACK対象にしない。
- LoRaの旧送信コマンド処理では、`Ss`付きのRF受信パケットを再送させない。
- 245 byteを超えるコマンドはGOLIDENでログ付き拒否とし、後続要求を止めない。

### 4.5 E220受信処理の修正

対象: [e220.h](../../src/components/LoRa/e220.h)、[e220.cpp](../../src/components/LoRa/e220.cpp)

同じ長さのパケットを繰り返し受信すると、以前の受信開始時刻を使い続け、RSSI有効時のタイムアウトが誤発火し得る処理を修正した。
追跡変数を初期化し、受信完了・長すぎるフレームの破棄後に長さ追跡をリセットする。
LoRa側でも、復号前にフレーム長・ヘッダ長・チェックサムを検証するようにした。

### 4.6 維持した通信設定

- E220長さバイト＋WCPP＋チェックサムの無線フレーム形式。
- チャンネル3、SF9／BW125、透過送信モード。
- ACKのPacket ID、`St`／`Ri`の意味。
- `Ss`付き受信パケットをSerialBusでPCへ配信する経路。

## 5. 追加した動作ログ

| ログ | 表す状態 |
| --- | --- |
| `[Tracker] Telemetry sent (UART accepted, Seq: ...)` | テレメトリをE220へUART送信したこと |
| `[Tracker] Uplink received & ACK sending... (Packet ID: ...)` | ACK優先キューへの投入成功 |
| `[GOLIDEN] LoRa Rx -> SerialBus Tx (Packet ID: ...)` | MainがLoRa由来パケットを観測したこと。PCへの配信はSerialBusが独立して行う |
| `LoRa busy: TX retained for retry` | 送信要求を保持してビジー解除を待っていること |

既存フレームワークの`'#'`パケット、`Ms`文字列として出力する。
USB Serialに平文を混在させず、WCPP対応モニタで確認する。

## 6. アップリンク不通の調査と解消

初回の実機報告では、COM21でTrackerのテレメトリを受信できた一方、アップリンク／ACKと`sent packet`が確認できなかった。
調査時点のファイルとプロセスを確認したところ、次の不一致があった。

| 役割 | パス | 調査時の状態 |
| --- | --- | --- |
| コマンド作成先 | `C:\WOBC\.command` | 278 byte。正常な`'t'` commandが17件 |
| COM21／COM19モニタの監視先 | `C:\Users\numat\.command` | 0 byte |

実行中のAnaconda版`wcpp-util`は、相対パス`.command`を開いていた。
両モニタの起動フォルダが`C:\Users\numat`だったため、`C:\WOBC`に追記したコマンドは読み込まれなかった。
実際のインストール済みパーサで作成済み17件を正常に復号でき、パケット生成失敗ではないことを確認した。

また、`command_file.seek(0, 2)`により起動前のパケットは読み飛ばされる。
作成済みファイルの最終更新は20:26:57で、調査時のモニタ起動より前だった。
正しいファイルを監視することに加え、モニタ起動後に新しいコマンドを作成する必要があった。

ユーザーがCOM21モニタの起動フォルダを`C:\WOBC`へ変更した後、テレメトリとACKの併用を確認した。
この段階ではPythonソースやファームウェアの変更は行わず、起動ディレクトリ・手順の修正で解消した。

## 7. 再現可能な起動・送信手順

### GOLIDENモニタ（Anaconda Prompt）

既存COM21モニタを終了してから起動する。

```bat
cd /d C:\WOBC
wcpp-util -p COM21
```

### Trackerモニタ（別のAnaconda Prompt）

GOLIDENと同じ`.command`を読ませないよう、別フォルダで起動する。

```bat
cd /d C:\Users\numat
wcpp-util -p COM19
```

### コマンド作成（モニタ接続後、別のターミナル）

```bat
python C:\WOBC\src\library\wcpp\python\send_command.py --packet-id t --component-id 0x10 --data "uplink" --command-path C:\WOBC\.command
```

作成先を絶対パスで指定し、COM21モニタ起動後に1件ずつ生成する。
両モニタを`C:\WOBC`から起動すると同じコマンドが両USBへ送られるため、この構成では避ける。
`[SUCCESS]`はファイル追記成功、`sent packet`はモニタによるシリアル書き込みであり、ACK到達とは区別する。

### 8.2 実機での併用確認

証拠は、ユーザーの成功報告と本会話で提供されたCOM21画面。以下は添付画面から読み取れた値を記録したもの。

| 項目 | 画面の値 | 解釈 |
| --- | --- | --- |
| 接続先 | COM21 | GOLIDEN経由のPCモニタ |
| 送信コマンド | component `0x10`、Packet `0x74 (t)` | ツリー表示時刻20:47:44 |
| ACK | component `0x10`、Packet `0x61 (a)` | ツリー表示時刻20:47:45 |
| ACK type | telemetry | ACKの既存形式 |
| ACK size | 12 bytes | `Ss`を含む受信パケットの表示サイズ |
| `St` | `0` | ACKの成功ステータス |
| `Ri` | `116` | `0x74`、文字`'t'`への応答 |
| `Ss` | `-37` | GOLIDENでLoRa受信時に付与されたRSSI値 |
| Trackerの定期テレメトリ | unit `0x61`、component `0x00`、Packet `0x4D (M)` | ツリー表示時刻20:53:14 |

ACKは既存のlocal形式を維持しているため、ツリーではunit `0x00`配下に表示される。
ACKのPacket ID `0x61 ('a')`とTrackerのunit ID `0x61`は別の識別子であり、混同しない。
今回の`Ss`付きACK受信とユーザー報告により、定期テレメトリを動かした状態でアップリンク／ACK経路が成立したことを確認した。

時刻は画面に表示された値であり、厳密な往復遅延の測定値ではない。
ACK後にも20:53:14のTrackerテレメトリ更新が見えるが、全パケットを記録した連続ログではないため、その間の無欠落を示すものではない。

## 9. 今後の確認項目

今回の実機確認により、初期資料の「実機での併用未確認」は解消した。
一方、次の定量評価はまだ行っていない。

- 多数回のコマンド送信に対するACK成功率・遅延分布。
- テレメトリ周期の前後で送信した場合の衝突率。
- 長時間運用時の欠落・重複・キュー使用量。
- AUX／UARTと空中占有時間の実測によるガード値の調整。

今回確認した実機条件での動作実績として記録し、無制限の連続投入やあらゆる電波条件での無損失保証とは区別する。
