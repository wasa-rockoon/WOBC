# NVSのモジュールID不一致による起動停止

## 概要

ESP32版WOBCでは，書き込まれたモジュールのIDをNVS（不揮発性ストレージ）に保存している．
NVSに保存済みのIDと，現在のファームウェアが指定するIDが異なる状態でID検査を有効にすると，`assert`により処理が停止する．

この停止は`serial_bus.begin()`より前に発生するため，USBシリアル自体が正常でもハートビートを含むパケットが一切出力されない．

## 調査状況

基板とUSBシリアルの正常動作を確認した後，`kernel::begin(module_id, false)`へ変更したTrackerファームウェアを書き込んだところ，実機でハートビートの受信が復旧した．
この結果から，NVSに保存されていたモジュールIDとTrackerのモジュールID `0x54`の不一致が原因だったと確定した．

## 発生した症状

- Trackerファームウェアは正常にビルド・書き込みできる．
- USBシリアルを使用した最小診断プログラムでは，`BOOT`と`alive`を正常に受信できる．
- GPIO42のSTAT LEDも正常に点滅する．
- 通常のTrackerファームウェアへ戻すと，パケット表示プログラムでハートビートを受信できない．

以上から，基板の電源，ESP32，GPIO42，USB配線，USB CDC，COMポートおよび書き込み機能は正常と判断できる．
問題箇所は`kernel::begin()`以降の初期化処理に絞られる．

## 原因となる処理

TrackerではモジュールIDとして`0x54`を使用している．

```cpp
constexpr uint8_t module_id = 0x54;
```

通常は次のように，モジュールID検査を有効にしてカーネルを初期化する．

```cpp
if (!kernel::begin(module_id, true)) return;
```

`kernel::begin()`はNVSの`KVS`名前空間を開き，キー`0xFFFF`に保存された1バイトのモジュールIDを読み出す．
ID検査が有効な場合，現在のIDと保存済みIDが一致することを`assert`で検査する．

```cpp
if (check_module_id) {
    assert(module_id == module_id_stored);
}
```

例えば，同じESP32基板へ以前GSファームウェアを書き込んでいた場合，GSのID `0x47`がNVSに残っている可能性がある．
その後Trackerファームウェアを起動すると，`0x54 != 0x47`となり，カーネル初期化の途中で停止する．

NVSは通常のファームウェア書き込みでは消去されないため，プログラムを書き換えただけでは保存済みIDが残る．

## ハートビートが出ない理由

ハートビート用タイマーの作成と開始は，モジュールID検査より後に実行される．

```text
NVSを開く
  ↓
保存済みモジュールIDを検査
  ↓ 不一致の場合はassertで停止
ハートビートタイマーを開始
  ↓
serial_busを開始
```

ID不一致で停止した場合，ハートビートタイマーもSerialBusタスクも開始されない．
そのため，パケット表示プログラムからは「何も送信していない」ように見える．

## 切り分け方法

### 1. 最小プログラムで基板とUSBを確認する

`Serial.println()`による文字列出力とGPIO42の点滅だけを行うプログラムを書き込む．
文字列とLEDの両方が正常なら，ハードウェアとUSBシリアルは原因から除外できる．

### 2. 正しいPlatformIO環境を書き込む

PlatformIOの環境として`Tracker`を明示的に選択して書き込む．
書き込み後はUSB CDCのCOMポートが再認識される場合があるため，パケット表示プログラムのポートを開き直す．

### 3. モジュールID検査を一時的に無効化する

Trackerの`kernel::begin()`を一時的に次のように変更する．

```cpp
if (!kernel::begin(module_id, false)) return;
```

`false`の場合，保存済みモジュールIDが存在すれば，そのキーを削除してからカーネルを起動する．
NVS全体を消去する処理ではなく，WOBCがモジュールIDに使用するキーだけが対象となる．

このファームウェアを書き込み，ハートビートを受信できるようになれば，保存済みモジュールIDの不一致が原因だったと判断できる．

今回の実機では，この変更後にハートビートを正常に受信できたため，NVSの保存済みモジュールID不一致が原因であることを確認できた．

## 解決結果

`kernel::begin(module_id, false)`で起動することにより，NVSに残っていたモジュールIDのキーが削除され，カーネル，ハートビートタイマーおよびSerialBusが正常に起動した．
その結果，パケット表示プログラムで約1秒ごとのハートビートを受信できるようになった．

基板，USBシリアルおよびパケット表示プログラムに異常はなく，通常のファームウェア書き込みでは消去されずに残っていたNVSの値が直接の原因だった．

## 復旧手順

1. `kernel::begin(module_id, false)`に変更する．
2. PlatformIOの`Tracker`環境でビルド・書き込みする．
3. 基板を起動し，パケット表示プログラムでハートビートを確認する．
4. `kernel::begin(module_id, true)`へ戻す．
5. 再度`Tracker`環境でビルド・書き込みする．
6. 再起動後もハートビートを受信できることを確認する．

手順4以降の起動では保存済みIDが存在しないため，`true`で起動した際に正しいTracker ID `0x54`がNVSへ保存される．

`false`のまま運用すると，起動時のモジュールID検査が機能しない．そのため，ID解除と動作確認が済んだら必ず`true`へ戻す．

## 正常時に期待されるパケット

カーネルが正常に起動すると，約1秒ごとにハートビートが生成される．Trackerの場合の主な内容は次のとおり．

- パケット種別: Telemetry
- パケットID: `0x22`（`'"'`）
- Component/Module ID: `0x54`
- `Im`: `0x54`
- `Iu`: `0x61`

現在のTrackerコードではLoRa，GPS，Pressure，Loggerなどの`begin()`がコメントアウトされているため，それらのテレメトリは出力されない．この状態でもカーネルのハートビートは出力される．

## `false`でもハートビートが出ない場合

モジュールID不一致以外を調べる必要がある．次の順で確認する．

1. `kernel::begin()`の戻り値が`true`か確認する．
2. `serial_bus.begin()`まで処理が到達しているか確認する．
3. SerialBusタスクの生成が成功しているか確認する．
4. ハートビート生成時に`kernel::packetCount()`が増えているか確認する．
5. パケット表示プログラムが，末尾のCRCとNUL区切りを含むWOBCパケット形式に対応しているか確認する．

確認用の文字列を同じ`Serial`へ出力するとWOBCのバイナリパケットへ混入するため，診断時は通常のシリアルモニターへ切り替えるか，別のUARTを使用する．

## NVS全消去について

フラッシュまたはNVS全体を消去する方法でも復旧できるが，他の設定値も失われる．
最初から全消去するのではなく，まず`kernel::begin(module_id, false)`によるモジュールIDキーだけの解除を推奨する．

## 再発防止

- 書き込み時はPlatformIOの対象環境を明示する．
- 別モジュール用ファームウェアへ変更する場合は，保存済みIDの解除手順を実施する．
- `false`は診断・ID変更時だけ使用し，通常運用では`true`にする．
- 将来的にはID不一致を`assert`だけで処理せず，専用LEDやデバッグUARTで原因を通知する仕組みを検討する．
