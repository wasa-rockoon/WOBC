# ヒーター制御

ヒーターの温度制御と更新停止監視はMCP3424のCH1だけを使用する。
CH2・CH3の計測とテレメトリ送信は継続するが、それらの温度や取得失敗は制御条件に含めない。

- CH1が40℃未満ならON、40℃以上ならOFF。
- INA226の電圧が6.4 V未満ならOFF。起動直後の電圧未取得時もOFF。
- CH1の正常取得から2,000 ms以上経過したらOFF。
- CH1の入力電圧が既存の有効範囲（0.05 Vより大きく2.00 V未満）から外れる場合、または温度計算が無効なら、期限を待たずOFF。
- 起動時および更新停止・異常後は、CH1の正常取得が3回連続するまでOFF。復帰中の通信失敗は連続回数をリセットする。
- 同じ温度値の連続取得も正常更新として数える。I²C送信失敗、受信不足、変換未完了、ADC設定の不一致では最終成功時刻を更新しない。

取得側は共有状態だけを更新し、ヒーターコンポーネントのタスクが約20 ms周期で状態を判定してGPIOを操作する。
取得を行う共通タイマーが停止しても、コンポーネントタスクが実行されていれば更新期限後にOFFになる。
停止時刻にはタスクの実行遅延が加わる。CPU全体の停止やGPIO・スイッチ素子の故障を検出する仕組みではない。

テレメトリの `Hs` は出力制御タスクが最後に適用した状態を示す。

| Hs | 意味 |
| --- | --- |
| ON | 加熱中 |
| OFF | CH1が目標温度以上 |
| OFF_LOW_BATT | 低電圧 |
| OFF_TEMP_STALE | CH1未取得または更新期限切れ |
| OFF_TEMP_INVALID | CH1の測定値が無効 |
| OFF_TEMP_RECOVER | 正常取得3回を待機中 |

測定失敗時、`Ca`・`Cb`・`Cc`には従来どおり最後の有効値が残る。値だけで更新成功を判断しないこと。
取得処理自体が停止するとテレメトリも止まるため、OFF動作はGPIOまたは負荷電流で確認する。
2秒の期限と3回の復帰回数は `src/components/Heater/HeaterControl.h` で定義する。

## 検証

ホスト上の制御テスト:

```powershell
g++ -std=c++14 -Wall -Wextra -I . tests/heater_control_test.cpp src/library/wcpp/cpp/Packet.cpp src/library/wcpp/cpp/float16.cpp -o .pio/heater_control_test.exe
& ./.pio/heater_control_test.exe
```

実機ではCH1の断線、ADC通信切断、取得タスクの停止、CH2・CH3だけの異常、CH1復旧、低電圧時の出力を確認する。
